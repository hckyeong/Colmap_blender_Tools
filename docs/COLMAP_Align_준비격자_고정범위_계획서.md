# Align 준비 단계의 고정 범위 격자 재사용 계획

- 작성일: 2026-09-20
- 상태: 0.3.61 구현·벤치마크·빌드·설치 검증 완료.
- 기준: 0.3.60과 현재 사용자 프로젝트의 3점 정렬 입력.
- 목적: 검사점 묶음이 달라져도 같은 범위의 검색 격자를 재사용한다.

## 1. 변경 요약

지금은 검사할 점을 8,192개씩 바꿀 때마다 검색 지도의 범위도 바뀐다. 이전 지도를 보관해 놓았어도 범위가 다르므로 버리고 다시 만든다.

개선 후에는 **준비를 시작할 때 두 메시 전체가 들어가는 지도 범위를 한 번 정한다. 이후 모든 검사점 묶음이 그 범위를 사용한다.** 기준 메시를 검색할 때 한 번, 역방향으로 이동 메시를 검색할 때 한 번 격자를 만든다. 여기서 역방향은 거리 검사의 방향을 바꾸는 것이며 메시를 실제로 이동시키는 것이 아니다.

현재 사례의 목표는 **격자 생성 18회 → 2회, 재사용 0회 → 16회**다. 메모리 예산 때문에 단계가 낮아지는 경우의 정상 재생성은 별도로 집계한다.

이번 구현은 Blender Align의 준비 입력 전달, C++ 워커, 배포용 CCCoreLib 패치를 함께 수정한다. 실제 ICP 내부의 회전·이동·배율 계산과 수렴 조건은 이번 범위에 포함하지 않는다.

## 2. 확인된 원인과 기준선

현재 열린 프로젝트에서 직전 3점 정렬 행렬을 지정하여 계산 입력을 다시 추출했다. 직전 실제 Align 실행과 형상 지문, 초기 행렬, 정규화, 등록 표본 및 양방향 평가 표본 지문이 일치한다.

| 항목 | 재계측 결과 |
|---|---:|
| 입력 정리 및 준비 실행 | 43.322초 |
| 그중 표본 준비 함수 | 34.606초 |
| 준비 거리 호출 | 18회 |
| 격자 생성 / 재사용 | 18회 / 0회 |
| 배포 바이너리 격자 생성 합계 | 18.984초 |
| 대상별 최초 생성 | 2회 |
| 같은 대상에서 경계 변경으로 재생성 | 16회 |
| 그중 칸 크기도 변경 | 13회 |
| 같은 대상에서 격자 단계 변경 | 0회 |

동일 검사점을 다시 넣은 대조군에서는 격자 재사용이 성공했다. 계측 바이너리와 배포 바이너리의 거리 결과도 바이트 단위로 일치했다. 재사용 기능 자체와 메모리 예산에 따른 단계 변경이 이번 실패 원인은 아니다.

현재 코어는 `대상 메시 경계 ∪ 이번 검사점 묶음 경계`를 정육면체로 확장하여 격자와 검사점 옥트리의 좌표계를 만든다. 검사점 묶음이 달라지면 이 경계가 달라지고, 캐시의 정확 일치 검사에서 실패한다. 이 구조는 [CCCoreLib 공식 거리 계산 소스](https://github.com/CloudCompare/CCCoreLib/blob/master/src/DistanceComputationTools.cpp)와 대조했으며, 실제 적용 판단은 배포된 고정 커밋과 패치 원문 및 계측 결과를 기준으로 한다.

재현 자료는 저장소에서 제외되는 `build/verification/grid-cache-cause-20260920/`에 있다. 핵심 자료는 `preparation-reproduction-live.json`, `cache-cause-live.json`, `live-input/source.json`, `source-identity.json`, `결과.md`다. 다른 환경에서는 동일 프로젝트 입력을 다시 확보한다. 사용자 입력과 대용량 바이너리를 제품이나 커밋에 넣지 않는다.

## 3. 구현 설계

### 3.1 준비 단계 전체의 범위를 한 번 확정

1. 기존 3점 정렬 적용, 계산용 퇴화면 정리, 공통 정규화를 그대로 수행한다.
2. 정규화된 이동 형상 전체와 기준 형상 전체의 경계를 구한다. 기준이 여러 개면 현재 계산에 쓰는 합쳐진 기준 형상 전체를 포함한다.
3. 두 경계를 합쳐 준비 단계의 불변 검색 범위로 보관한다. 검사점 배열을 모두 미리 만들거나 메시 좌표를 추가 복제하지 않는다. 이미 계산한 전체 경계가 있으면 재사용한다.
4. 범위를 입력 형상·초기 행렬·정규화에 종속된 식별자와 함께 준비 거리 명령에 전달한다. 정육면체 확장과 셀 좌표 계산은 C++에서 한 번의 동일한 규칙으로 수행한다.
5. 탐색점, 정렬 표본 선별점, 독립 평가 표본 선별점에 모두 같은 범위를 사용한다. 새 검사점 옥트리는 해당 묶음의 점으로 만들되, 좌표계는 고정된 격자와 일치시킨다.

메시 표면에서 뽑는 점은 원래 메시 경계 안에 있으므로 전체 형상 경계로 준비 단계의 모든 묶음을 포함할 수 있다. 단정도 변환과 표면 보간에서 발생하는 끝자리 오차까지 포함하도록 경계를 바깥쪽으로 보수적으로 변환하고, 기존 정육면체 확장의 여유와 평면축 보정을 유지한다. 최초 묶음의 범위만 저장하거나 임의의 배율로 크게 잡지 않는다.

### 3.2 기존 거리 경로와 고정 범위 경로를 분리

코어에는 고정 범위를 명시하는 별도 진입점 `computeCloud2MeshDistancesWithCacheAndBounds`를 추가한다. 기존 `computeCloud2MeshDistances`와 `computeCloud2MeshDistancesWithCache`의 공개 시그니처와 기본 동작은 유지한다. 내부 계산은 공통 구현으로 연결하여 거리 계산 코드를 복제하지 않는다.

새 경로는 정확한 비부호 점–삼각면 거리 계산에만 적용한다. 변경하는 것은 격자와 검사점 옥트리의 공통 범위이며, 실제 삼각면 거리 계산은 그대로 사용한다.

고정 범위를 받은 경우 다음을 검사한다.

- 최소·최대 값의 개수, 유한성, 순서와 단정도 표현 가능 여부.
- 대상 메시 전체와 이번 검사점 전체가 실제 공통 큐브 안에 포함되는지.
- 옥트리에 모든 검사점이 투영되었는지. 범위 밖의 점을 잘라내거나 누락한 채 성공하지 않는다.
- 같은 범위 식별자로 전달된 경계값이 명령 사이에 변하지 않았는지.

선언한 범위를 벗어나면 명확한 입력 오류로 종료하고 기존 확정 결과를 보존한다. 잘못된 범위를 조용히 확대하거나 기존 느린 경로로 우회하여 결함을 숨기지 않는다. 고정 범위를 요청하지 않은 연산은 기존 정상 경로를 사용한다.

### 3.3 재사용 조건과 수명

캐시는 현재와 같이 **동시에 한 개만** 보관한다. 두 방향의 격자를 동시에 유지하지 않는다.

| 상황 | 처리 |
|---|---|
| 같은 대상·범위·실제 단계, 검사점 묶음만 변경 | 격자 재사용 |
| 준비 방향 전환으로 대상 메시 변경 | 이전 격자 해제 후 새 대상 격자 생성 |
| 형상·초기 정렬·정규화 또는 선언 범위 변경 | 다른 준비 문맥으로 처리하고 기존 격자 무효화 |
| 가용 메모리 감소로 실제 단계 하향 | 기존 격자를 해제한 후 낮은 단계로 재생성 |
| 등록 시작 또는 준비 범위를 쓰지 않는 명령으로 전환 | 고정 범위 문맥과 해당 격자 초기화 |
| 취소·오류·세션 종료 | 격자를 메시보다 먼저 해제 |

대상, 공통 큐브의 최소·최대 경계, 실제 단계, 셀 크기의 **정확 일치 검사 자체는 유지**한다. 범위 식별자만 같다는 이유로 실제 경계 검사를 생략하지 않는다.

### 3.4 명령 계약과 적용 범위

새 네이티브 거리 명령에는 `search_domain`을 추가한다. 준비 단계에서 메시를 대상으로 하는 거리 계산에만 식별자와 최소·최대 좌표를 전달하고, 다른 명령은 `null`을 사용한다. 같은 준비 문맥에서 값이 바뀌는 입력과 허용하지 않은 단계·연산의 사용은 거부한다.

명령의 고정 필드가 달라지므로 네이티브 프로토콜을 `cccore-native-v5`로 갱신한다. Python 요청 생성·응답 검증, C++의 요청 검증·환경 검사, 빌드 Manifest를 함께 변경하여 구버전 실행 파일과 혼합되지 않게 한다. 기존 v4 실행 계약에 새 필드를 몰래 끼워 넣지 않는다.

Blender 작업 Manifest와 저장된 정렬 이력은 필요한 실행 식별 정보 외에는 기존 의미를 유지한다. 과거 승인 기록과 확정 행렬을 계속 읽고, 현재 작업의 실행 파일 검증과 과거 기록 읽기 검증을 구분한다. 표본 정책, 시드, 개수와 품질 기준은 바꾸지 않는다. 실행 빌드가 다른 거리 결과 캐시를 새 계산에서 재사용하지 않는다.

최적화 적용 대상은 준비 단계의 메시 거리 조회다. 점군 간 거리, 준비 이후 변환된 표본의 거리 평가, 실제 ICP 등록 내부 반복은 기존 경로와 초기화 규칙을 유지한다. 메시–점군 등 혼합 입력에서도 메시를 대상으로 하는 준비 조회만 고정 범위를 사용한다.

## 4. 메모리와 정확도

기존 포인터 격자 예산 `min(256 MiB, min(가용 물리 메모리, 가용 커밋 메모리) / 16)`과 조회 실패 시의 기존 제한을 유지한다. 명령마다 가용량을 다시 확인한다. 고정 범위라고 해서 격자 단계를 강제로 유지하지 않는다.

예산이 부족하면 실제 단계를 낮추고, 같은 대상의 연속 호출에서는 낮아진 단계를 유지하여 메모리 회복에 따른 반복 확대를 피한다. 새 격자 할당 전에 이전 격자의 용량을 반환한다. 유지할 수 있는 단계가 없으면 기존 오류 처리를 따른다.

추가 상주 정보는 경계 좌표, 식별자와 단계 값이다. 메시 배열, 모든 검사점, 전체 거리 배열 또는 대상의 전체 옥트리를 새로 상주시키지 않는다. 포인터 배열 제한은 전체 프로세스 메모리 상한이 아니므로 실제 작업집합과 커밋도 별도로 측정한다.

격자 범위가 달라지면 셀 배치와 삼각형 방문 순서는 달라질 수 있다. 따라서 수학적으로 같은 정확 거리라는 이유만으로 기존 결과와 모든 부동소수점 비트가 같다고 가정하지 않는다. 거리값은 기존 허용오차와 해석적 정답으로 검증하되, 합격 여부·제안 수·표본 좌표·출처·순서는 그대로여야 한다. 이 항목이 달라지면 원인을 해결하기 전 배포하지 않는다. 허용오차나 반경을 늘려 통과시키지 않는다.

코어 패치 식별자는 `mesh-grid-fixed-domain-v1`로 추가한다. 기존 패치 단계의 원문 해시를 덮어쓰지 않고, 새 패치 이후 최종 해시를 별도로 연결한다. LGPL 재빌드 원문과 변경 고지에 반영한다. `.cccore-runtime/cache`의 수동 수정만으로 배포하지 않는다.

새로 작성하거나 수정하는 함수에는 간단한 한국어 설명을 붙인다. 임시 비교 로그는 검증 도구에서만 사용하고 제품에는 남기지 않는다. 현재 다른 작업이 수정 중인 UI·Modifier·문서 파일은 포함하지 않는다.

## 6. 검증 순서

### 1단계: 작은 입력에서 실패와 수정 확인

- 같은 메시를 대상으로 검사점 묶음의 범위만 바꾸어 기존 경로의 반복 생성을 재현한다.
- 수정본에서 고정 범위를 사용하면 첫 생성 이후 재사용되는지 확인한다.
- 범위가 없는 기존 API는 같은 입력에서 기존 동작을 유지하는지 확인한다.
- 넓은 삼각형 일부에만 가까운 점, 평면 메시, 얇고 긴 형상, 경계 위·안·밖의 점과 단정도 반올림 경계를 검사한다.
- 단일 스레드와 병렬 실행에서 해석적 거리 및 작은 메시의 전수 삼각형 비교값을 확인한다.
- 범위 누락·변경·유효하지 않은 값, 대상 전환, 등록 시작, 명령 수명, 취소·오류 후 재사용을 검사한다.
- 결정적인 예산 입력을 주는 검증으로 단계 하향·메모리 반환을 확인한다. 실제 컴퓨터의 메모리를 고의로 고갈시키지 않는다.

### 2단계: 현재 프로젝트의 준비 단계 먼저 비교

전체 ICP 완료를 기다리기 전에 이 단계에서 개선 여부를 판정한다.

1. 현재 프로젝트 또는 보존 입력의 형상·초기 행렬·정규화·시드·설정 지문을 확인한다. 기준선과 달라졌으면 새 기준선을 만들고 서로 다른 입력의 시간을 비교하지 않는다.
2. 동일 입력, 31스레드, 8,192점 묶음으로 기존·수정본의 실제 준비 함수를 각각 실행한다. 양쪽 모두 범위 산출과 새 명령 처리 비용을 포함한다.
3. 예열 후 기존·수정본을 번갈아 3회씩 순차 실행한다. 별도 성능 작업을 동시에 돌리지 않는다.
4. 준비 전체·표본 함수·격자 생성·거리 계산·프로토콜 시간을 나누고, 생성/재사용 횟수와 최대 메모리를 기록한다.
5. 메모리 단계가 안정된 현재 18개 호출에서 생성 2회·재사용 16회를 확인한다. 단계 하향 때문에 추가 생성이 있으면 사유와 횟수를 구분한다.
6. 같은 18개 명령 재생은 코어 비교의 보조 자료로 사용한다. Python 준비 함수의 실제 실행을 대신하지 않는다.

등록 표본 50,000개와 양방향 평가 표본 각 30,000개의 좌표·출처·순서를 비교한다. 탐색/합격 개수와 실제 호출 수도 일치해야 한다. 현재 표본 지문에는 거리값도 포함되므로 지문이 다르면 좌표·거리·출처를 분리해 원인을 확인한다. 거리만 기존 수치 허용 범위에서 달라도 원인을 기록하며, 합격점이나 순서 변화는 채택하지 않는다.

### 3단계: 제품 회귀와 실제 정렬

작은 입력의 네 형상 조합, 알려진 정답 변환, 부분 겹침, 품질 판정, 취소, 저장·복원을 검사한다. 새 프로토콜이 설치본의 응답 검증과 과거 기록 복원을 깨뜨리지 않아야 한다.

준비 단계의 효과를 확인한 뒤 지정 프로젝트의 같은 3점 정렬 시작 상태로 실제 Align을 한 번 검증한다. 현재 사용자의 결과를 취소하거나 덮어쓰지 않도록 보존된 입력·검증용 사본에서 시작 상태를 재현한다. 직전 564.010초 실행을 기준으로 전체 검증의 상한을 720초로 두고, 상한에 도달하면 그 검증 프로세스만 정상 취소하여 미완료로 보고한다. 중단 결과를 전체 정렬 시간이나 품질 성공으로 표시하지 않는다.

비교 항목은 준비·ICP·평가·전체 시간, 최종 행렬·배율, 고정된 독립 검사점의 오차, 품질 판정이다. 사용자 `.blend`와 OBJ의 변경 여부, 마커와 현재 미리보기 보존도 확인한다.

### 4단계: 빌드·배포

정확도·메모리·준비 속도 검증을 통과한 소스로 C++ Release와 확장 ZIP을 재빌드한다. 새 패치·DLL·원문 ZIP·Manifest·Python 검사값의 일치를 확인하고 격리 설치의 실제 정렬 검사를 수행한다. 실제 설치 시에는 실행 중인 Blender가 기존 DLL을 계속 사용할 수 있으므로, 새 프로세스에서 실행 식별자를 검증한 결과와 현재 열린 프로세스 상태를 구분해 보고한다.

설치·커밋·푸시는 구현 작업에서 완료 범위와 검증 상태에 맞춰 처리한다. 이번 계획 작성 중에는 제품 코드·설치본·현재 Blender 상태를 변경하지 않는다.

## 7. 완료 기준과 효과의 한계

| 항목 | 완료 기준 |
|---|---|
| 재사용 | 안정된 메모리 조건의 대표 입력에서 생성 2회·재사용 16회 |
| 속도 | 동일 입력 준비 시간의 중앙값 감소, 새 범위 계산 비용까지 포함 |

직전 실제 Align 전체는 564.010초였고, 두 ICP 계산이 490.857초를 차지했다. 이번 준비 단계 최적화만으로 전체 1분 미만을 달성하는 계획은 아니다. 준비 구간을 수정·검증한 뒤 ICP 내부의 별도 병목을 다음 대상으로 삼는다.

## 8. 구현·검증 기록

### 동일 프로젝트 준비 단계

현재 프로젝트에서 보존한 동일 3점 초기 입력을 사용했다. 이동·기준은 각각 정점 5,651,583개, 계산용 삼각면 11,303,380개다. 31스레드, 8,192점 묶음과 기존 모든 표본 정책을 유지했다. 예열 각 1회 후 기존·수정본을 번갈아 각 3회 순차 실행했으며 다음은 중앙값이다.

| 항목 | 기존 0.3.60 | 수정 0.3.61 |
|---|---:|---:|
| 입력 정리부터 준비 종료 | 43.954초 | 26.782초 |
| 표본 준비 함수 | 34.858초 | 17.852초 |
| 격자 생성 합계 | 18.931초 | 2.172초 |
| 실제 거리 커널 합계 | 3.702초 | 3.454초 |
| 거리 명령 수 | 18 | 18 |
| 격자 생성 / 재사용 | 18 / 0 | 2 / 16 |
| C++ 최고 작업 집합의 중앙값 | 724.6 MiB | 722.2 MiB |

준비 전체는 **39.07%**, 표본 준비 함수는 **48.79%** 단축했다. 예열을 포함한 네 쌍의 모든 거리 배열이 바이트 단위로 같았다. 등록 50,000점, 양방향 평가 각 30,000점과 전체 참고 표본의 좌표·출처·순서, 제안·합격 개수, 표본 지문도 같았다. 메모리 단계 하향에 따른 추가 생성은 없었다. 이 수치는 전체 Align 시간이 아니다.

재현 스크립트는 `tests/align/experiments/benchmark_fixed_domain_preparation.py`이며, 입력과 원시 결과는 배포·커밋에서 제외되는 `build/verification/fixed-domain-implementation/preparation-series/`에 보관했다. `summary.json`에 각 회차, 단계별 시간, 관측 메모리와 정확도 비교를 남겼다.

### 경계 접촉 결함과 호환성

새 범위의 평면 회귀에서 기존 `Grid3D.h`의 결함을 확인했다. 평면과 셀 꼭짓점의 내적이 정확히 0일 때 이를 양수로 처리하여, 접촉한 삼각형을 교차 후보에서 모두 제거할 수 있었다. 0을 중립으로 유지하여 기존 `TriBoxOverlap` 검사를 거치게 수정했다. 평면축 확대·정확 거리·예산·허용오차는 바꾸지 않았다. 공통 격자 교차 루틴의 수정이므로 기존 거리 API의 경계 접촉 누락도 바로잡는다.

기존 통합 검사 한 건은 이 오류의 비유한 거리 차단에 의존했다. 같은 입력을 이전 v4, 수정본의 기존 범위, 수정본의 고정 범위로 대조했다. 작은 접촉은 표본 부족으로 거부되고, 실제로 81점이 겹치는 큰 평면은 변환·개선 없는 `REVIEW`로 남는다. 수정본의 두 경로는 품질·행렬·평가 지표가 같다. 회귀는 이 의미를 검증하도록 두 건으로 나누었으며 제품 품질 정책을 변경하지 않았다.

과거 네이티브 v2·v3·v4 및 저장 스키마 7·8의 승인 이력 복원을 검사했다. 현재 실행은 v5 빌드만 허용하지만 기존 기록과 확정 행렬은 그대로 읽는다. 점군끼리의 준비에는 새 전체 경계 스캔을 추가하지 않는다.

### 배포 구성

이전 0.3.60 설치 ZIP에 이미 포함된 UI·Modifier 기능을 보존한 소스에 이번 Align 변경만 적용해 0.3.61을 구성한다. 작업 중인 다른 파일을 이번 커밋에 포함하지 않는다. 새 코어 패치, `Grid3D.h` 고정 커밋 원문, 적용 전후 해시, Release DLL과 재빌드 원문 ZIP을 함께 검증한다.

### 실제 Blender 전체 Align

별도 Blender 5.2.0 프로세스의 격리 설치본에서 `Untitled.blend`를 열었다. 보존한 마커 3쌍으로 실제 마커 미리보기 연산자를 실행한 뒤 초기 행렬·RMS·형상 지문·설정을 대조하고 실제 Align 연산자를 호출했다. 현재 사용자의 Blender 프로세스와 결과에는 손대지 않았다. 아래 전체 시간은 프로젝트 복원과 3점 미리보기 재구성 시간을 제외한 Align 호출부터 결과 반영까지다.

| 항목 | 이전 실제 실행 | 수정 설치본 실행 |
|---|---:|---:|
| 준비 | 44.312초 | 27.047초 |
| 강체 ICP | 271.816초 | 281.156초 |
| 배율 보정 ICP | 219.041초 | 234.119초 |
| 전체 Align | 564.010초 | 573.048초 |
| 최종 품질 | PASS | PASS |

**준비 단축은 확인했지만 이번 전체 실행은 약 9초 더 걸렸으며, 전체 시간 단축을 확인하지 못했다.** 두 ICP의 합계는 490.857초에서 515.275초였다. 전체 실행은 각 한 번이므로 이 차이를 특정 원인이나 일반적인 성능 회귀로 단정하지 않는다. 준비 단계의 3회 비교 결과와 구분한다.

모든 후보의 독립 평가 지표가 기존과 같고, 추가 배율은 양쪽 모두 `0.9845334565075224`다. 저장한 등록 행렬로 재구성한 이전 최종 행렬과 새 최종 행렬의 최대 절대 차이는 `1.39e-17`이다. 최종 평가 RMS도 `9.270844894488799e-08`로 같다. 원본 OBJ와 `.blend`의 크기·수정 시각을 보존했고, 검증 프로세스는 저장 없이 종료했다. 원시 자료와 비교는 `blender-operator-run/`, `blender-comparison.json`에 기록했다.

### 최종 검증·설치

- 정식 C++ Release의 네이티브 회귀 47개, Python 전체 통합 회귀 55개, 네이티브 계약·이력 복원 회귀 15개 통과.
- 확장 빌드의 필수 구조·통합 등록 검사와 스테이징 실제 정렬 통과.
- ZIP 격리 설치의 네 형상 조합, 승인·되돌리기·다시 실행, 환경설정 및 OBJ 입출력 검사 통과.
- 사용자 설치본 0.3.61을 별도 Blender에서 불러와 배포 파일 1,175개와 네이티브 v5 신원을 대조했다. 사용자 환경설정 해시가 같다.
- ZIP SHA-256: `38c79623323a8e639d4edc68d9b828074c9d66eaf146d8eb706f6ef8befeac7e`.

실행 중이던 Blender는 기존 Python 모듈을 유지하므로 재시작 후 새 버전을 사용한다. 현재 미리보기와 마커를 보존하기 위해 활성 세션의 강제 재적재는 하지 않았다.
