# OBJ CPU 배열 준비 재사용

## 범위와 보존 계약

`codex/artec-align-engine`의 OBJ 가져오기에서 CPU 배열 준비만 개선한다. 원본 Blender Mesh와 정점·면·코너·UV·재질·원본 ID 대응, 등록 정점의 오름차순 순서를 보존한다. 네이티브 OBJ 파서, 정렬 엔진, GPU 배치·마커 선택 경로는 변경하지 않는다.

- 한 동기 검증에서 읽은 좌표와 코너 정점 배열을 프록시 생성에 전달한다. 검증된 임시 배열을 장기 캐시하거나 다음 가져오기에 재사용하지 않는다.
- 모든 원본 면이 삼각형임을 검사한 경우에만 코너 배열과 순차 원본 면·코너 번호로 동일한 삼각형 프록시를 구성한다. `calc_loop_triangles()`와 개수 확인은 유지한다. Quad·N-gon 혼합 입력은 기존 Blender 삼각분할 순서를 사용한다.
- 등록 정점은 검증된 삼각형에서 사용 여부를 표시해 원본 번호 오름차순으로 생성한다. 미사용 정점은 원본에 남기며, 등록 입력에서는 기존처럼 제외한다.
- 코너 정점과 면 재질은 영역·자료형·길이를 검사한 속성 배열에서 읽는다. UV는 활성 레이어의 벡터 배열을 float32로 추출한 뒤 기존 float64 계약으로 변환한다.
- 전체 정점을 표시하는 새 가져오기는 이미 같은 표시 배열을 가진 모델을 재사용한다. 명시적으로 더 작은 표시 상한을 지정하면 기존 샘플링과 모델 검증을 유지한다.
- 공개 전체 형상 검증, 실패·취소 정리, 복원 사전 점검 뒤의 실제 형상 검증, 저장 형식과 출처 검사를 유지한다.

## 검증 계획

삼각형·혼합 면, UV 경계·재질, 미사용 정점, 손상 입력, 명시적 표시 제한, 가져오기·복원·원본 ID·내보내기 회귀를 검사한다. 같은 대용량 OBJ를 보존한 변경 전 소스와 변경 후 소스로 별도 GUI 프로세스에서 번갈아 측정한다. 비교 대상 두 모듈 외의 소스와 GPU 렌더링 코드는 동일하게 유지하고, 전체 배열의 SHA-256과 단계별 시간을 비교한다. 사용자 장면과 원본 파일을 저장하거나 수정하지 않는다.

Blender의 삼각형 삼각분할은 원본 코너 `(0, 1, 2)`를 그대로 사용한다. [Blender 5.2 공식 구현](https://github.com/blender/blender/blob/v5.2.0/source/blender/blenkernel/intern/mesh_tessellate.cc)

## 측정 조건

- 날짜: 2026-10-21. Blender 5.2.0 LTS, Ryzen 9 7950X3D, RTX 4090, 메모리 128GB.
- 입력: 현재 장면에서 사용한 `Gilt-bronze Pensive Maitreya Bodhisattva 78_high poly.obj`, 7,640,571,796바이트.
- 정점 30,109,486개, 삼각형 60,206,247개, UV 코너 180,618,741개. 표시 정점도 30,109,486개 전체를 사용한다.
- 변경 전 → 변경 후를 세 번 교대한다. 매번 공장 초기 상태의 별도 GUI 프로세스를 사용하며, 사용자 Blender는 열린 상태를 유지한다. 운영체제 파일 캐시는 비우지 않는다.
- 변경 전에는 작업 시작 전에 보존한 `embedded_obj_store.py`, `mesh_importer.py`를 사용한다. 두 파일의 SHA-256은 현재 설치본과도 같다. 나머지 의존 코드와 렌더러는 변경 후 조건과 같다.
- 총 작업 시간은 가져오기 작업의 각 `step()` 시간을 합산한다. 파일 읽기, CPU 준비, GPU 배치 준비, 확정을 포함한다. Blender 실행·측정 기록 저장·전체 배열 해시·최초 비교 화면 그리기는 제외한다. 따라서 최초 화면 표시까지의 사용자 체감 전체 시간을 직접 잰 수치는 아니다.
- 실제 GPU 검증은 같은 256×256 투영에서 텍스처 배치 22개를 그린 뒤 전체 픽셀의 SHA-256을 비교한다. 다른 카메라 위치와 모든 화면 크기를 측정한 것은 아니다.

### 동일성과 회귀 검사

- 여섯 실행 모두 성공했다. 전체 배열 12개의 크기·자료형·SHA-256·읽기 전용 상태가 모두 일치했다. 정점, 삼각형, 등록·표시 정점, UV, 재질 번호, 원본 면·코너 대응과 경계를 포함한다.
- 전체 정점 30,109,486개를 그대로 표시했다. 삼각형 수와 UV 코너 수도 동일하며, 속도를 위해 원본 또는 표시 정점을 줄이지 않았다.
- 22개 텍스처 배치로 그린 비교 화면의 전체 픽셀이 모두 동일했다. 픽셀 SHA-256은 `f68533f87a0746b4e541734e408b5f902dedfa2fa5b6aa89f87bc2bdbc3131b2`다.
- 원본 OBJ의 크기와 수정 시간이 모든 실행 전후 및 실행 사이에 같았다.
- 소스 회귀 검증 스크립트 50개가 모두 통과했다. 신규 검사 4개는 삼각형 순서·UV 경계·재질·미사용 정점, 혼합 면의 Blender 삼각분할, 전체 표시 재사용·명시적 표시 제한, 손상 코너 거부를 검증한다.
- Python 문법, UTF-8 인코딩, 변경 파일의 공백 오류 검사도 통과했다.

### 반영 상태와 재현 자료

브랜치 소스의 런타임 변경은 `tools/align/mesh_io/embedded_obj_store.py`와 `tools/align/mesh_importer.py`에 한정한다. 원본 검증의 공개 계약과 명시적 표시 상한 동작을 유지한다. 삼각형만 있는 입력의 중복 추출은 제거하고, 혼합 면에서는 기존 Blender 삼각분할 배열 추출을 유지한다. 표시·마커 GPU 버퍼 공유, 네이티브 파서 교체, 정렬 엔진 변경은 포함하지 않는다.

## 기본 Blender 가져오기와 직접 비교

### 비교 방법

같은 7.64GB OBJ를 기본 Blender와 CPU 준비를 개선한 애드온으로 각각 새 GUI 프로세스에서 가져왔다. 현재 사용자 장면과 설치본은 유지했다. 이 비교의 애드온은 현재 실행 중인 설치본이 아니라 위 개선을 적용한 브랜치 소스다.

- 기본 경로: `bpy.ops.wm.obj_import('EXEC_DEFAULT', True, ...)`를 직접 실행한다. 전역 실행 취소 설정은 켜져 있고, 명령 호출에서도 실행 취소를 허용한다.
- 애드온 경로: 실제 가져오기 작업인 `MeshImportJob`의 읽기·CPU 준비·GPU 배치 준비·확정을 모두 실행한다.
- 양쪽 모두 축 `Y/Z`, 배율 1, 클램프 없음, 오브젝트·그룹 분할 없음, 메시 검증 활성화로 통일한다. 기본 가져오기 메뉴의 초기 축·분할 값 그대로가 아니라, 같은 형상을 비교하기 위해 옵션을 맞춘 기본 명령이다.
- 첫 번째 시간은 가져오기 명령 또는 작업이 완료되는 시점까지다. 두 번째 시간은 여기에 화면 투영 준비와 첫 1024×768 GPU 프레임의 픽셀 회수 완료까지 더한다. GPU 명령 제출 시점에서 타이머를 끝내지 않는다.
- 기본 화면은 Workbench의 `SOLID/TEXTURE`, `STUDIO`, 기본 안티앨리어싱 8 설정이다. 애드온 화면은 기존 표면 배치·셰이더를 사용한다. 같은 투영을 쓰지만 조명·안티앨리어싱 경로가 달라 양쪽 픽셀의 완전 일치를 조건으로 삼지는 않는다.
- 첫 GPU 프레임은 오프스크린 측정이다. 파일 선택, 프로세스 시작, UI 타이머 대기와 실제 창 합성 시간은 제외한다. 화면 표시 기능이 없는 파일 읽기 시간과 첫 화면 준비 비용을 구분하기 위한 비교이며, 파일 선택 버튼 클릭부터 실제 창 표시까지를 직접 계측한 수치는 아니다.
- 기본 → 애드온 순서로 교대하며 운영체제 파일 캐시는 비우지 않는다. 2회차에는 사용자 요청에 따라 실행 도중 창 관리 방식이 바뀌었으므로 원시 결과를 보존하되 최종 중앙값에서 제외한다. 한 쌍을 추가 측정해 1·3·4회차의 3개 값을 사용한다.
- 최종 실행기에는 Blender의 `--no-window-focus`를 적용했다. 새 테스트 창을 뒤에서 열고 포커스를 가져오지 않으며, 실행 중 해당 동작도 확인했다. 사용자 Blender 창은 조작하지 않는다.

첫 프레임의 기본 경로는 Blender의 [공식 오프스크린 뷰포트 API 구현](https://github.com/blender/blender/blob/v5.2.0/source/blender/python/gpu/gpu_py_offscreen.cc)을 사용한다. OBJ 명령의 옵션과 실행 취소 플래그는 [공식 OBJ 명령 구현](https://github.com/blender/blender/blob/v5.2.0/source/blender/editors/io/io_obj.cc)에 정의돼 있다.

### 직접 비교 결과

최종 3회 중앙값은 다음과 같다. 단위는 초다. 각 행을 독립적으로 집계하므로 개별 행의 중앙값을 더한 값은 총시간의 중앙값과 조금 다를 수 있다.

| 측정 구간 | 기본 Blender | 개선 애드온 | 애드온 추가 시간 |
|---|---:|---:|---:|
| 가져오기 명령·작업 완료 | 44.820 | 88.741 | 43.920초, 약 1.98배 |
| 가져오기 뒤 첫 GPU 프레임 | 4.516 | 2.443 | 아래 준비 단계와 함께 해석 |
| 가져오기 + 첫 GPU 프레임 완료 | 49.210 | 91.199 | 41.989초, 약 1.85배 |

애드온은 가져오기 작업 안에서 CPU 모델 준비 20.298초와 자체 GPU 배치 준비 22.527초를 사용했다. 그 앞의 OBJ 읽기·분리 단계는 45.882초였다. 전체 표시 재사용 단계는 0.000039초로, 이전 개선에서 제거한 재검증 비용은 다시 발생하지 않았다.

기본 Blender도 첫 그리기에서 GPU 준비 비용을 부담한다. 애드온의 첫 GPU 프레임만 2.443초로 더 짧아 보이는 이유를 전체 표시 경로가 더 빠르다는 뜻으로 해석하면 안 된다. 그 전에 애드온 작업에서 이미 GPU 배치 준비에 22.527초를 사용했기 때문이다. 이 모델의 전체 차이는 별도의 정렬·마커·표시용 CPU 배열 준비와 애드온 GPU 배치 준비에서 주로 발생했다. 이 가져오기 측정에는 KD-tree 구축이나 Align 실행이 포함되지 않는다.

| 회차 | 기본 가져오기 | 애드온 가져오기 | 기본 첫 프레임까지 | 애드온 첫 프레임까지 | 집계 |
|---|---:|---:|---:|---:|---|
| 1 | 44.436 | 82.491 | 48.952 | 85.186 | 포함 |
| 2 | 44.814 | 88.258 | 49.166 | 90.703 | 창 관리 방식 변경으로 제외 |
| 3 | 44.998 | 90.729 | 49.777 | 93.235 | 포함 |
| 4 | 44.820 | 88.741 | 49.210 | 91.199 | 포함 |

이번 애드온 가져오기 시간 범위는 82.491~90.729초다. 앞선 CPU 개선 전후 비교의 81.449초는 다른 시점의 측정 집합에서 나온 중앙값이다. 이번 실행에서도 개선된 소스의 SHA-256은 유지됐으며, 두 집합의 시간을 섞어서 비율을 계산하지 않았다.

### 직접 비교 검증 및 증거

- 기본·애드온 각 4회가 모두 완료됐으며, 위 기준에 따라 각 3회로 최종 비교했다.
- 양쪽의 정점 30,109,486개, 원본 면 60,206,247개, 코너 180,618,741개, UV 레이어 1개와 전체 경계가 같았다.
- 각 경로의 세 프레임 해시는 경로 내부에서 모두 같았다. 기본과 애드온 사이의 픽셀 색 차이는 서로 다른 표시 셰이더·조명 경로에 해당하며, 양쪽 프레임 모두 모델이 실제로 그려졌음을 확인했다.
- 모든 실행에서 원본 파일 크기·수정 시간과 비교 대상 소스 해시가 유지됐다. 이번 비교에서는 런타임 소스와 사용자 Blender 설치본을 수정하지 않았다.
- 마지막 실행에서 `--no-window-focus` 적용과 테스트 프로세스가 전면 창이 아님을 확인했다. 임시 창 관리 도우미는 종료·제거했고, 이후 테스트 실행기는 Blender 자체 옵션을 사용한다.
