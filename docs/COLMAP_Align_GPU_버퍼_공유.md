# Align 표시·마커 선택 GPU 버퍼 공유

이 문서 앞부분은 최초 GPU 배치 공유 당시의 기록이다. 현행 0.3.79의 위치 버퍼 분리와 첫 선택 지연 분석은 마지막 절에서 설명한다.

## 범위와 구현

2026-10-21, `codex/artec-align-engine`에서 기존 CPU 준비 최적화에 이어 표시와 마커 선택의 GPU 배치를 공유한다. 원본 정점·면·UV, 정렬 입력과 엔진, 피벗 BVH, 저장 형식, 점 표시 기능은 유지한다.

기존 텍스처 메시 경로는 분할 표시 배치 외에 전체 원본 정점의 위치·법선과 삼각형 인덱스로 마커 전용 배치를 만들었다. 이제 동일한 표시 `GPUBatch` 객체를 다른 선택 셰이더로 그린다. [Blender 5.2의 GPUBatch 구현](https://github.com/blender/blender/blob/v5.2.0/source/blender/python/gpu/gpu_py_batch.cc)은 호출 시 셰이더를 지정할 수 있다. 추가 위치·법선·인덱스 GPU 버퍼를 만들지 않는다.

- 화면 ID는 배치별 겹치지 않는 임시 정수 구간을 사용한다. 읽어 온 최대 9개 후보만 원본 삼각형 번호로 변환한다. 재질 순서와 원본 순서를 혼동하지 않는다.
- 모든 면이 한 텍스처 그룹에 속하면 원본 번호를 `range`로 보관해 전체 번호 배열도 만들지 않는다. 일부 면만 포함된 그룹은 읽기 전용 `uint32` 번호 배열을 한 번 만들고 분할 배치에서 슬라이스를 참조한다.
- 마커 최종 좌표는 기존대로 원본 `float64` 삼각형의 광선 교차에서 계산한다. 표면의 GPU 단정도 좌표나 깊이 역투영 값으로 대체하지 않는다.
- 공유하는 대상은 표시용 정점·속성·인덱스 배치다. 클릭 때마다 현재 카메라와 모델 변환으로 작은 ID·깊이 패스를 갱신하는 기존 동작을 유지한다.
- 256MiB 텍스처 버퍼 제한, UV 이음매와 재질별 표시 순서, 첫 클릭의 BVH 미생성, 모델 교체 시 캐시 무효화, 실패 정리 계약을 유지한다.
- 무텍스처 메시의 전체 면 배치는 기존처럼 직접 공유한다. 재질별 그룹 공유 래퍼는 필요할 때만 사용한다.

수정 대상은 `viewport/renderer.py`, `viewport/screen_pick.py`와 해당 회귀 검사다. 실제 GPU 회귀는 `tests/align/blender/test_shared_mesh_pick_gpu.py`에서 수행한다.

## 검증과 측정 방법

같은 7,640,571,796바이트 OBJ를 기본 Blender, 변경 전 애드온, 변경 후 애드온의 격리 프로세스에서 각각 3회 측정한다. 원본은 30,109,486개 정점, 60,206,247개 삼각형, 180,618,741개 모서리이며 UV를 유지한다. 변경 전 비교는 이 작업 직전에 보존한 두 GPU 모듈을 사용한다. CPU 가져오기 코드와 입력 조건은 같다.

Blender 5.2.0 LTS, RTX 4090에서 `--factory-startup --no-window-focus`와 숨김 창 실행을 사용한다. 사용자 Blender 세션은 변경하지 않는다. 파일·드라이버 캐시를 비우지 않고, 두 번째 회차의 실행 순서를 반대로 배치한다. 기본 가져오기와 애드온의 축·분리·원본 검사 옵션을 맞춘다.

가져오기, GPU 배치 준비, 첫 표면 프레임을 구분한다. 프레임은 1024×768 오프스크린 출력과 픽셀 읽기까지 포함한다. 애드온 첫 마커는 일반 화면을 한 번 그린 뒤 측정하며, 변경 전 마커 전용 배치의 최초 업로드 비용도 포함한다. 각 프로세스에서 같은 지점 20회 반복과 다른 두 지점도 확인한다. 첫 회차의 첫 지점은 전체 원본 삼각형을 검사하는 독립 교차 기준으로 검증한다. 파일 지문·배열 검사·독립 교차 시간은 가져오기 시간에 포함하지 않는다.

시작 프로세스·파일 선택창·UI 타이머 대기·창 합성은 측정 범위 밖이다. 기본 Blender와 애드온의 셰이딩은 다르므로 두 방식 간 픽셀 일치를 요구하지 않는다. 변경 전후 애드온의 모든 픽셀과 원본 배열 지문은 같아야 한다. 측정 로그는 `build/verification/obj-shared-gpu-20261021/`에 보존한다.

## 결과

각 방식 **3회 중앙값**이다. GPU 배치 준비와 읽기 후 준비는 전체 가져오기 시간에 이미 포함된다.

| 측정 경계 | 기본 Blender | 공유 전 애드온 | 공유 후 애드온 |
|---|---:|---:|---:|
| 가져오기 완료 | 42.945초 | 82.211초 | 82.823초 |
| 읽기 후 CPU·GPU 준비 | — | 39.339초 | 38.432초 |
| 그중 GPU 배치 준비 | — | 21.812초 | 21.063초 |
| 가져오기 + 첫 표면 프레임 | 47.318초 | 84.836초 | 85.235초 |
| 첫 마커 선택 | 해당 기능 없음 | 618.845ms | 18.182ms |
| 반복 마커 선택 | 해당 기능 없음 | 9.108ms | 16.429ms |

GPU 배치 준비는 **0.749초, 3.43% 감소**했다. 읽기 후 준비는 **0.906초 감소**했다. GPU 준비의 세 회 범위는 공유 전 21.427~21.989초, 공유 후 21.048~22.288초로 겹친다. 작은 중앙값 차이가 모든 실행에서 재현되는 것은 아니다. 전체 가져오기 중앙값은 전후 **+0.612초** 차이다. 파일 읽기 등 나머지 단계의 변동이 포함되므로 전체 차이를 GPU 공유의 효과로 전부 돌리지 않는다. 기본 Blender 대비 공유 후 전체 가져오기 시간은 **1.93배**다.

첫 마커 선택은 **97.06% 감소**했다. 공유 전의 첫 클릭에는 아직 그리지 않은 별도 선택 배치의 최초 업로드가 필요했다. 공유 후에는 이미 표면을 그릴 때 업로드한 22개 배치를 그대로 사용한다. 준비 단계의 개선보다 첫 클릭의 개선이 훨씬 크다.

반복 선택은 **7.320ms 증가**했다. 기존 선택 배치는 원본 정점을 인덱스로 재사용했지만, 공유하는 텍스처 배치는 UV를 보존하려고 면 모서리별로 펼친 정점을 22번의 그리기 호출로 처리한다. 이번 자료에서는 반복 선택이 약 16~17ms 수준이며 모든 데이터·GPU에서 같은 결과를 보장하지 않는다.

선택 전용 위치·법선·인덱스 데이터 **1,445,102,628바이트(약 1.45GB, 1.346GiB)**를 제거했다. 이는 실제 생성 배치의 속성과 인덱스 개수로 계산한 형상 버퍼 크기이며 드라이버의 총 VRAM 사용량을 직접 측정한 값은 아니다. 이 모델은 한 텍스처 그룹이므로 원본 번호 매핑에 별도 CPU 배열을 사용하지 않는다. 여러 재질이 섞인 자료는 필요한 면 번호를 `uint32` 배열로 보관한다.

공유 후에도 CPU 모델 준비 17.369초와 표시 배열·법선·GPU 배치 준비 21.063초가 필요하다. 기본 Blender와의 차이가 사라진 것은 아니다. 이 측정에 KD-tree 구축이나 Align 실행은 포함되지 않는다.

### 정확도·회귀·수명

- 변경 전후 6개 실행에서 원본 관련 **12개 배열**의 전체 SHA-256·형상·자료형·읽기 전용 상태가 일치했다. 정점·원본 면 매핑·모서리 매핑·UV·재질과 표시·등록 인덱스를 포함한다.
- 변경 전후 **1024×768 전체 RGBA 픽셀**이 일치했다. 텍스처 분할은 22개로 같으며 GPU 배치 객체가 표시와 선택에서 실제로 동일함을 확인했다.
- 동일한 3개 화면 위치에서 원본 삼각형 ID와 최종 배정밀도 좌표가 일치했다. ID는 `54965523`, `129076`, `36755487`이다. 첫 지점의 원본 **60,206,247개 전체 삼각형** 독립 교차 검사에서도 두 방식 모두 같은 ID와 좌표가 나왔고 좌표 오차는 0이었다.
- 소스 회귀 **50개**가 통과했다. 별도 실제 GPU 검사에서 원근·직교·배면·음수 및 비균일 변환·깊이 24개 경우, 교차 재질·누락 UV·청크 경계 8개 면, 재질이 다른 면의 앞뒤 겹침 2개 경우, 큰 정수 ID 3개 경우, 픽셀 일치 2개 경우와 실패 시 GPU 상태 복원·모델 교체·자원 해제를 확인했다.
- 테스트 창은 포커스를 가져오지 않게 실행했다. 측정 중 전경 프로세스가 VS Code이고 테스트 Blender가 아님을 확인한 기록을 보존했다.

## 0.3.79 첫 선택 지연 분석과 위치 버퍼 분리

2026-10-21, `codex/artec-align-engine`에서 0.3.78의 선택 경로를 계측했다. 이전 UV 검증에서 기록한 1.5968274초 사건에는 세부 프로파일이 없으므로 그 사건의 원인을 소급해 확정하지 않는다. 동일한 사용자 두 모델의 읽기 전용 선택 검사에서는 첫 선택 0.0566012초와 0.4460712초를 관측했다. 느린 0.4460712초 중 `GPUFrameBuffer.read_color` 대기가 0.4425758초였고, 그리기 제출은 합계 약 0.00058초, 원본 정밀 교차는 약 0.00050초였다. 경로에 CPU UV 재생성·BVH·KD-tree 생성은 없었다.

같은 호출 전후 DXGI가 보고한 해당 프로세스의 지역 GPU 메모리 사용량은 282,009,600 → 6,064,054,272 → 11,844,263,936바이트로 증가했다. 각 증가분은 모델당 위치·법선·UV 버퍼 5,779,799,712바이트와 거의 같다. GPU 자원을 다시 사용하는 비용이 동기 결과 읽기에서 대기로 드러났다는 근거다. 드라이버의 퇴거 이벤트 자체를 추적한 결과는 아니며, 9픽셀의 작은 결과 전송량이 443ms를 소모했다고 해석하지 않는다. [Microsoft의 GPU 메모리 예산 설명](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/nf-dxgi1_4-idxgiadapter3-queryvideomemoryinfo)도 예산·상주 변경이 실행 성능에 영향을 줄 수 있음을 설명한다.

표시용 단일 정점 버퍼를 위치 12바이트와 법선·UV 20바이트로 나눴다. 표시 배치는 두 버퍼를 참조하고, 선택 배치는 같은 위치 버퍼만 참조한다. 무텍스처 경로도 위치·법선을 분리하며 두 배치가 인덱스 버퍼 하나를 공유한다. 이는 [Blender의 복수 정점 버퍼 API](https://docs.blender.org/api/5.2/gpu.types.html#gpu.types.GPUBatch.vertbuf_add)를 이용한다. GPU 배치 객체는 두 개지만 위치·인덱스를 복제하지 않으며 모델 간 공유도 없다.

- 선택에서 참조하는 형상 속성은 모델당 5,779,799,712 → 2,167,424,892바이트로 **62.5% 감소**한다. 표시까지 포함한 전체 GPU 형상 데이터가 62.5% 감소한다는 뜻은 아니다.
- 원본 CPU 배열, UV 코너 순서, 재질별 분할과 원본 삼각형 번호 매핑은 바꾸지 않는다. 최종 마커 좌표는 원본 `float64` 삼각형 교차로 결정한다.
- 버퍼 객체·배치·선택 셰이더는 불러오기 중 준비한다. 클릭에서 큰 배열이나 선택 전용 형상 버퍼를 생성하지 않는다. 실제 업로드 시점과 이후 상주는 Blender·드라이버가 관리하므로 GPU 메모리의 영구 상주를 보장하지 않는다.
- 원본 유지·다른 모델 자원 격리·실패 정리·캐시 무효화 계약을 유지한다. 이전에 되돌린 OBJ 계산 제거는 재도입하지 않는다.

검증 자료는 `build/verification/marker-first-20261021/`에 보존한다. 기존 두 모델 각각 정점 30,109,486개·삼각형 60,206,247개이며 원본 파일, 1024×768 화면, 세 선택 지점을 고정한다. 정상 화면을 그린 뒤 첫 선택과 반복 선택을 비교하고, 별도로 첫 표시 이전에 선택해 GPU 최초 업로드 비용을 분리한다. 선택 시간은 프로파일 파일 저장·집계 비용을 제외한 실제 선택 함수의 벽시계 시간이다. 두 경계를 섞어 1.60초 개선율을 계산하지 않는다.

GPU 최초 업로드를 포함한 중앙값은 **58.02% 감소**했다. 이미 GPU 자원이 준비된 정상 선택의 속도 개선은 확인하지 않았다. 변경 후 정상 첫 선택 한 건의 50.79ms 중 46.95ms도 GPU 결과 읽기 대기였다. 따라서 모든 최초 클릭이 16ms라는 주장이나 과거 1.60초가 완전히 제거됐다는 주장을 하지 않는다. 이번 네 회차의 최대값에는 의도적으로 포함한 최초 업로드 선택이 들어가며, 이를 정상 표시 후 클릭 지연과 섞지 않는다.

불러오기·준비 단계 합계는 정상 표시 조건에서 173.467 → 173.243초였다. 첫 전체 표시까지 더하면 178.195 → 185.297초로 해당 회차는 느려졌다. 최초 업로드를 따로 측정한 회차에서는 그 선택과 첫 표시까지 합친 시간이 181.073 → 178.436초였다. 파일 캐시와 GPU 상주·드라이버 상태를 고정하지 않았으며 전체 불러오기나 첫 표시의 속도 개선은 주장하지 않는다. 변경의 직접 효과는 선택에서 불필요한 표시 속성을 참조하지 않도록 줄인 것이다.

### 정확도와 배포 확인

- 네 회차, 총 여덟 모델의 전체 정점·삼각형·UV·원본 면/코너 매핑 지문과 1024×768 표시 픽셀이 모두 일치했다. 세 지점의 원본 삼각형 ID는 `54965523`, `129076`, `36755487`이며 배정밀도 좌표도 같았다. 정상 비교 회차의 첫 지점은 각 모델의 60,206,247개 전체 원본 삼각형을 검사하는 독립 기준과 대조했고 좌표 오차는 0이었다.
